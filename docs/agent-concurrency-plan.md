# Agent 系统并发改进方案

> 目标：在**不引入多副本、不换向量库、不加消息队列**的前提下，让系统能应对一定量并发。
> 思路：单进程 + 四道闸门 —— **限流 / 队列 / 缓存 / 降级**。
> 预计改动量：约 40 行代码 + 3 个启动参数。

---

## 一、先明确三类接口的不同上限

"高并发"对这三类接口的含义完全不同，**不能定同一个目标**：

| 接口类型 | 单次耗时 | 可行上限 | 说明 |
|---|---|---|---|
| 搜索 / 列表 | ~50-200ms | 几百 QPS | 便宜：CPU 嵌入 + MySQL 查询 |
| 图片索引 / 智能补充 | 30-60s | 十几个 | 慢且贵：每次都要调 VL 模型 |
| 对话（Agent） | 10-30s | 几十~上百并发 | 瓶颈是模型 API 的 QPS/TPM，不是服务器 |

**推论**：搜索要"提速"，索引要"排队限流"，对话要"快速拒绝 + 限并发"。

---

## 二、四条改进

### ① 限流

**做法**

- 三个服务的启动参数加并发上限（超限直接拒绝，不排队）：
  - Agent（8000）：`limit_concurrency = 64`
  - 索引服务（8001）：`limit_concurrency = 32`
  - Qwen 网关（8080）：`limit_concurrency = 16`
- Agent 的准入控制用中间件实现：在途请求数超过阈值 → **429 + Retry-After**，返回 JSON 让前端能提示
- `app/main.py` 把 AnyIO 线程池上限从默认的 40 调到 100

```python
import anyio
anyio.to_thread.current_default_thread_limiter().total_tokens = 100
```

**为什么**：每个对话会占住一个线程十几秒（模型等待），默认 40 就是并发天花板。
**为什么拒绝而不是排队**：排队会让所有请求一起变慢，最后一起超时；快速拒绝 + 让用户重试，整体体验更好。

### ② 队列

**不加新组件。** Java 里的 `pictureIndexExecutor` 已经在做"提交到后台池"，只需要：

- 把池子并发调到 **2~4**：每张图都要调一次 VL 模型，一次提交几十张会直接撞 DashScope 限流
- 长任务保持"提交后立即返回 + 日志观察进度"的现有形态

### ③ 缓存

**只做一件事，但收益最大**：让 DeepSeek 的前缀缓存生效。

现状问题（`app/graph/nodes.py`）：

```python
messages = [SystemMessage(content=system_prompt)] + list(messages)
#                            ↑ 里面拼了本轮检索到的长期记忆，每轮都不同
```

system prompt 一变，**整段对话的前缀缓存全部失效** —— DeepSeek 的自动前缀缓存要求前缀逐字节相同，system 位于最前面，后面全部重算。

**改法**：

1. system prompt 固定为静态常量（不含记忆）
2. 本轮检索到的记忆，**追加到当前这轮 user 消息的末尾**
3. 只在「一轮对话的开始」注入（最后一条是 human 消息时），避免每次工具调用都重复检索

改完前缀变成 `[静态 system + 追加式历史]`，稳定不变 → 长对话的成本和延迟明显下降。

⚠️ 注意：注入的记忆只存在于本次推理的本地消息列表里，**不写回 state**，否则会污染历史永久留痕。

**其余缓存不用加**：列表缓存（版本号失效 + TTL 抖动 + 单飞）已经做得比多数项目完善。

### ④ 降级

**已有**：Redis 熔断 ✓、语义搜索失败→关键词 ✓、记忆 fail-closed ✓、VL 失败→纯文本索引 ✓

**补齐三处**：

1. **Java 调 8001 的检索要短超时**：现在"生成索引"和"检索"共用同一个 `RestTemplate`，读超时 180 秒。
   → 加一个专用的 `RestTemplate`（连接 1s / 读 2s），超时即走关键词兜底。
   否则 8001 一慢，Tomcat 线程会被成片拖住。
2. **过载统一返回 429**（含 `Retry-After`），而不是 500。
3. **前端区分「繁忙」与「失败」**：429/503 提示"服务繁忙，请稍后重试"，不要显示成报错。

## 三、明确不做什么

| 不做 | 原因 |
|---|---|
| 多副本 / `uvicorn --workers N` | 进程内状态（对话历史 `MemorySaver`、图片队列 `session_store`）会让多副本出现**正确性 bug**（丢图、串历史），不是性能问题 |
| 状态外移（Postgres checkpointer / Redis session） | 单进程够用；真要多副本时必须先做 |
| 换向量库（Chroma → pgvector） | SQLite 单写者在单进程下不是瓶颈 |
| 消息队列 / Celery | 现成线程池够用 |
| 流式输出（SSE） | 体验提升明显，但属于形态改变，单独立项 |

**代价**：单进程单实例，上限 = 本机 CPU × 模型 API 配额。对"几十并发"够用，且不引入新 bug。

---

## 四、顺带修掉的一个 bug

`app/session_store.py` 是**无锁 dict**，而工具运行在线程池里：
同一会话并发两条消息时，A 的上传可能把 B 刚存入的图片清掉。

→ 加 per-session 锁（约 15 行）。

---

## 五、验证方式

写一个压测脚本（`scripts/loadtest.py`，基于 `httpx.AsyncClient`）：

- 搜索路径：可放心压 20 / 50 / 100 并发
- 对话路径：**小额度**压（每次调用都是真实模型费用）

输出 **p50 / p95 / p99 + 错误率 + 吞吐**。

改动前后各跑一次，用于确认：
1. 限流阈值是否合理（错误率应来自 429，而不是超时）
2. 缓存改动是否降低了对话延迟
3. 并发上限到底在哪（曲线拐点）

---

## 六、实施顺序

```
1. 限流        —— 启动参数 + 中间件 + 线程池上限
2. 降级        —— Java 检索短超时 + 前端 429 提示
3. session 加锁 —— 正确性 bug
4. 缓存        —— system prompt 静态化
5. 压测脚本    —— 前后对比
```

每一项都可独立验证、独立回滚。
